# Windows 测试构建（GitHub Actions）

使用 `.github/workflows/windows-test-build.yml` 在 GitHub 托管的 Windows
runner 上生成桌面测试包。**构建完成后只提供产物地址，不替用户下载、解压、
启动或安装**；本机无需安装 Rust、MSVC 或完整的前端构建依赖。

上游同步和 SSH 定制改动的保留流程见
[SSH 与上游更新维护指南](../maintenance/ssh-upstream-sync.md)。

这是开发测试流程，不是正式发布流程：不创建 Release、不打版本标签，
也不发布自动更新清单。远端机器仍可使用已有的 `codeg-server` 预编译包。

配套的 `src-tauri/tauri.windows-test.conf.json` 仅为本次构建覆盖
`bundle.createUpdaterArtifacts: false`，不修改正式发布配置。构建会生成包含
`codeg-mcp` 伴生程序的 NSIS 安装包，不是一个可单独复制运行的裸应用 EXE。

桌面更新配置继续指向上游 `xintaofei/codeg`，保留新版本检查和提醒。
不生成测试包自己的更新产物，不等于禁用应用内更新；确认安装上游包仍可能替换
包含 SSH 定制功能的桌面版本。查看上游更新和维护自己的 Fork 构建是两件事。

## 首次在 Fork 中启用

1. 在自己的 Fork 中启用 GitHub Actions。如果 Actions 页面提示工作流被禁用，
   先确认并启用。仓库或组织的 Actions 策略也必须允许所使用的 actions。
2. 将本工作流及其配套配置通过 Pull Request 合并到 **自己 Fork 的默认分支**
   （通常为 `main`）。不要误向原作者仓库提交这个仅供个人测试的 PR。
3. GitHub 的 `workflow_dispatch` 工作流必须存在于默认分支，才能正常从
   Actions 页面登记并手动运行。只把文件推送到开发分支，可能看不到
   **Run workflow** 按钮。
4. 此后可以从 **Run workflow** 的分支下拉框选择开发分支；被选择的分支也应
   包含本工作流及配套配置。分支早于工作流的引入时，先同步这些文件。

本流程不需要原作者的 `TAURI_SIGNING_PRIVATE_KEY`、Apple 签名凭据或
Release 写入权限。GitHub 托管 runner 的额度、缓存和产物存储费用，
以你自己的账户及仓库设置为准。

## 运行与地址交付

1. 打开自己的 Fork → **Actions**，选择 Windows 测试构建工作流。
2. 点击 **Run workflow**，选择要测试的分支并运行。
3. 等待构建和原生 SSH 验证成功，确认本次运行页面的 **Artifacts** 区域存在
   Windows 产物且未过期（当前默认保留 14 天）。
4. 核对运行页面的提交 SHA，提供产物地址、运行地址、SHA、检查结果和有效期。
   GitHub Artifacts 访问可能需要登录；提供地址后即完成交付，不在本机下载、解压或安装。

首次运行通常需要下载依赖并冷编译；缓存只能加速后续兼容的构建，
不能保证每次命中。重新运行工作流仍使用 GitHub runner，不会转为本机编译。

## 交付和验证边界

- 测试包未作正式发行签名，Windows 可能提示未知发布者或 SmartScreen 警告。
  只运行自己信任的仓库、工作流和提交生成的产物，不要全局关闭系统保护。
- 不应假定测试版与正式版的数据、安装目录和应用标识相互隔离。后续是否使用
  产物由用户决定；不擅自覆盖日常使用的安装或执行应用内更新。
- 保留正式版更新检查和提醒，但不把安装上游包当作保留 SSH 定制功能的升级方式。
  更新 Fork 源码后运行本工作流，只交付对应提交的产物地址。
- 当前工作流包含编译、打包和原生 Windows SSH 密码验证，但不能替代实际桌面的
  手工验收。仅如实注明未验证项目，不为了验收而替用户安装或启动产物。
- 这项工作流本身不实现 SSH 功能；它为后续代码修改提供测试包构建渠道。

## 常见问题

### 看不到工作流或 Run workflow 按钮

确认 Actions 已启用、本工作流已进入自己 Fork 的默认分支，且当前账号
有运行工作流的权限。不要通过打正式版本标签来绕过此问题。

### 构建提示需要签名私钥

确认运行的是测试工作流而非 `release.yml`，且选中分支包含关闭 updater
产物签名生成的测试配置。本流程不应要求复制原作者的发行私钥。

### Artifacts 中没有安装包

先检查运行是否成功，以及构建、打包和上传步骤的日志。失败构建不应被当成
可用测试包；产物超过保留期后也需要重新运行工作流。

### 缓存没有显著加速

检查是否修改了 Rust 工具链、依赖锁文件、目标平台或缓存配置。首次运行、
缓存淘汰和分支间缓存可见性都可能导致冷构建，不需要因此在本机重新编译。
